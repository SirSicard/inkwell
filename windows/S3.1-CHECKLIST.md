# Windows platform checklist (S3.1)

The unit tests cover every decision in `ink-platform-win` (mic routing, the far-end plan, the
detection debounce and denylist, the hotkey machine, the insertion order, the clipboard formats,
the capture wake under `assert_no_alloc`). The audio-service tests (`cargo test -p ink-platform-win
-- --ignored`, the device, session and detector ones) run over SSH. This list covers what only a
desktop session shows: capture from real calls, the keyboard hook, pasting into other apps, and an
elevated target.

## Setup

Run everything from a normal (not administrator) PowerShell in your own desktop session, from
`core/`:

```powershell
cargo build -p ink-platform-win --example win_check
$check = ".\target\debug\examples\win_check.exe"
```

The binary prints levels, counts and verdicts, never audio. It never prints text you selected,
only its length. Every capture also prints an I4 line (allocations in real capture wakes), which
must be `PASS I4: 0 allocations`.

## The call matrix (step 7)

One real test call per app, each 60 s, with the app already in the call before the check starts.
Speak when the call plays you back. Run both commands in the same call.

| App (executable) | `--capture 60` (device loopback) | `--capture 60 --app <exe>` (plan printed) | Detection (`detect: +` line) |
|---|---|---|---|
| New Teams (`ms-teams.exe`) | | | |
| Zoom (`Zoom.exe`) | | | |
| Meet in Chrome (`chrome.exe`) | | | |
| Meet in Edge (`msedge.exe`) | | | |

Fill each capture cell with `Signal` or the verdict printed, and each detection cell with the
executable printed (or `none`). Expected from S0.4: device loopback hears every call; the `--app`
run is device loopback on the app's own output for Teams (per-process loopback is known silent on
new Teams) and process loopback for Zoom and the browsers.

## Record

Green when lines 1 to 14 and the matrix pass. Record anything else that looks wrong: a non-zero
`discontinuities`, `skipped`, `untimed` or `overruns`; `MMCSS false`; `detector: N read errors`
above 0; and any exe name step 8 printed.

## Known limits (not failures)

- Windows removes a keyboard hook that stalls for about a second, without telling the app. Loss
  detection is probabilistic: the heartbeat is sampled only near real input (every 5 s while you
  type), so a removed hook is noticed within about 5 s of the next typing, and a key pressed in
  that gap is missed. A reinstall keeps a hold in progress (the core's stuck-hold watchdog ends it
  if its release was lost); after three reinstalls in ten minutes the hotkey reports Lost.
- A multichannel output that refuses its own layout is captured in stereo; nothing tells the user
  or the core (the checklist binary prints `x2`).
- Focus moving between the start of an insertion and its Ctrl+V (or a typed batch) stops it with
  "the focused window changed"; the window is too short to stage by hand, so unit tests cover it.
- A clipboard manager or remote-desktop sync that reads the clipboard as soon as it changes makes a
  paste unconfirmable (step 12b), and may keep the dictated text in its own history: the
  exclusion formats bind only Windows' clipboard history and cloud sync.
- An app that ignores Ctrl+V gets "nothing was inserted", never typed text: typing after a posted
  paste could insert the text twice if the paste lands late.
- The microphone check reads the three privacy switches, not the Group Policy / MDM keys
  (AppPrivacy `LetAppsAccessMicrophone`); a policy-denied mic records silence, which the core's
  watchdog reports.
- Saving the clipboard copies every format whatever its size (a large image is copied whole).
- For a UWP app the foreground process is `ApplicationFrameHost.exe`, not the app.
- Process loopback captures the first process tree of that name (lowest root pid) when several
  run separately.
- The detection denylist matches executable names only; a renamed executable is not recognised.
- Injected key events from other tools (remote desktop, automation) are treated as typed, so they
  can press the hotkey.
- With `right_alt` on a layout with AltGr, Windows sends a fake left Ctrl with it, which is not
  swallowed.
- A key released while the secure desktop is up (a UAC prompt, the lock screen), or inside an app
  running as administrator, is not seen; the core's stuck-key watchdog ends that hold.
- Right Ctrl as the hotkey is swallowed while held, so right Ctrl+C does not copy; left Ctrl does.
- The Copilot key is not bound yet: that needs the packaged app to register as the key's provider
  (S3.6).
